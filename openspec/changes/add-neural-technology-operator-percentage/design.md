## Context

Neural Technology compatibility output is built from ML SDK Model Converter
records. Each record can describe an operation that lowers to TOSA for NX, an
operation routed through EE/Shader support, or an unsupported operation. The
standardized compatibility payload already exposes per-operation placement in
the entities list, but it does not yet emit the result-level
`accelerator_operator_percentage` metric.

The NX Performance Estimator path is separate. Its standardized performance
output already emits the standard metric as unavailable, and the current
performance source does not provide trustworthy placement percentages for
EE-routed operations.

## Goals / Non-Goals

**Goals:**

- Add the standardized `accelerator_operator_percentage` metric to
  compatibility output.
- Derive the metric from the existing compatibility records without adding a
  new backend call.
- Keep EE/Shader-routed operations compatible while excluding them from the
  accelerator numerator.
- Keep unsupported operations in the denominator so partial compatibility does
  not overstate accelerator coverage.
- Emit an availability-aware metric when the compatibility result has no
  records.

**Non-Goals:**

- Do not change NX Performance Estimator output for this metric.
- Do not treat EE/Shader-routed operations as accelerator-placed.
- Do not add a new consumer-specific report shape.
- Do not change the existing entity placement values or compatibility statuses.

## Decisions

### Compatibility records are the source of truth

`NXModelCompatibilityInfo.to_standardized_output()` should compute the metric
from the records already used to build checks and entities. This keeps the
result aligned with the visible per-operation placement table and avoids
duplicating converter analysis.

Alternative considered: compute the value from performance output. That path
does not expose trustworthy placement coverage for EE-routed operations, so it
should continue to emit the standard performance metric as unavailable.

### NX placement is the only accelerator numerator

The numerator should count only records whose placement is `NX`. EE/Shader
records remain successful compatibility records, but they are not counted as
accelerator-placed for this standardized metric.

Alternative considered: count all non-CPU records as accelerated. That would
classify EE/Shader routing as accelerator placement and would make the metric
less useful for consumers that need NPU/NX coverage.

### All compatibility records remain in the denominator

The denominator should include NX, EE/Shader, and unsupported records. This
means a partially compatible model reports the percentage of all converted
operations that are actually placed on NX, not the percentage of only supported
operations.

Alternative considered: divide by only compatible records. That would hide
unsupported operations and overstate accelerator placement for partially
compatible models.

### Empty compatibility output is unavailable

When there are no records, the output should use an availability-aware metric
entry instead of emitting `0%`. A numeric zero would imply the converter
observed operations and placed none on NX; empty output instead means no
placement data is available.

## Risks / Trade-offs

- Consumers might expect the same metric in compatibility and performance
  output to have the same availability. Mitigation: keep the source semantics
  explicit and leave performance output unavailable until a trustworthy
  performance source exists.
- Counting unsupported operations in the denominator can produce lower values
  than a "supported-only" percentage. Mitigation: this matches the result-level
  operator coverage question and avoids overstating accelerator placement.
- The calculation depends on stable placement labels. Mitigation: reuse the
  existing `placement` values generated by compatibility record construction and
  cover NX, EE/Shader, unsupported, and empty cases in tests.

## Migration Plan

This is an additive standardized-output metric. Existing checks, entities, and
compatibility statuses remain unchanged, so no migration is required for
current consumers.
